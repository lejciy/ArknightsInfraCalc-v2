# AI 辅助代码审阅操作指南

> 文档角色：current-reference
> 生命周期状态：current
> 当前真源：docs/质量与维护/QUALITY_AND_AUDIT.md；docs/质量与维护/SYSTEM_AUDIT_WORKFLOW.md
> 摘要：将现有 AI 审阅规则组织为可执行步骤、材料清单和任务模板，区分通用方法与 v2 验证入口

## 1. 用途与适用范围

本页把 v2 已有的协作和复审规则整理成操作手册，供主代理组织审阅，也供人检查审阅是否完成。它不新增审批点、强制产物或业务规则；具体约束以以下来源为准：

- [根协作规则](../../AGENTS.md)：授权、工作区、分工、验证与提交。
- [意图复审 skill](../../.agents/skills/arknights-intent-review/SKILL.md)：审阅准绳、取证方向、独立判断和发现处置。
- [质量与验证总则](QUALITY_AND_AUDIT.md)：风险分层、保证等级、证据和无人值守边界。
- [正式体系审计工作流](SYSTEM_AUDIT_WORKFLOW.md)：仅在用户要求严格逐项审计或领域权威文档冲突时使用。

先选择本次工作方式：

| 用户要求 | 执行到哪里 |
|---|---|
| 只读审查、诊断或建议 | 收集证据并交付发现；修复作为待授权动作 |
| 已授权修复 | 完成实现、风险匹配验证、必要的独立复审和原子提交；推送与部署另按授权处理 |
| 正式体系审计 | 按正式审计工作流，在审计报告和修改计划之后分别等待用户裁决、批准 |

中高风险的选人、排班、导出或跨模块变更，在整个功能完成后进行独立意图复审。纯文档和低风险局部改动按风险裁剪，不必机械套用全部角色、材料和全局验收。

## 2. 通用思路

把审阅组织成三条可以相互核对的线：

| 线索 | 要回答的问题 | 依据 |
|---|---|---|
| 要求 | 应该实现什么，哪些行为必须保持？ | 用户原话、已确认决策、改动前的领域文档 |
| 实现 | 谁作判断、谁改变状态、谁消费结果？ | 实际代码、调用方、下游和旧路径 |
| 证据 | 什么输入能支持或推翻当前结论？ | 合法案例、最小非法案例、最终状态、真实运行产物 |

最小的审阅记录是：**要求或下游前提 → 对应代码 → 触发输入 → 预期与实际行为 → 原始证据 → 处理结果**。

例如，“缺少必需成员时不得形成有效方案”是一条要求。审阅应找出准入阶段如何保证它，并用缺成员的输入挑战该保证；当前样本恰好选中了全部成员，只能说明这次结果，不能说明规则已被完整实现。

## 3. 操作原则

1. **标准来自改动之外。** 用户当前裁决优先；本次修改的文档与代码一起接受审阅，不能用它们互相证明正确。
2. **先读要求，再读实现。** 先列出合法条件、禁止状态和保持条件，避免把代码现状当成需求。
3. **取证与判断分工。** 调查者返回原文和位置；审阅者作独立判断；主代理回到原始材料核对并处置。关键结论和否定结论尤其需要原文支持。
4. **保持审阅上下文独立。** 使用新上下文，不传入实现者的根因解释、预期结论、自评或上一位审阅者的结论。
5. **查结构保证和最早违规位置。** 找到负责该规则的模块，检查顺序、状态写入、失败和回退路径；同时检查重复计算、样例特判和冲突旧路径。
6. **检查验证是否有辨别力。** 验证应能区分合法与最小非法状态，不能只是复述实现的判断或复用同一个错误假设。
7. **让结论匹配证据覆盖。** 区分事实、推断和未知；构建成功、样本通过、审阅批准各自只支持有限结论。涉及搜索空间变化时按质量总则说明保证等级。
8. **每条发现有明确去向。** 已修复、有证据驳回或交给用户裁决；代码改变后重新核对最终版本，旧证据不直接替代新版本验收。

## 4. 角色与责任

| 角色 | 负责 | 边界 |
|---|---|---|
| 用户 | 确定意图、产品语义、范围和需要裁决的取舍 | 日常授权内的局部修复不逐步重复审批 |
| 主代理 | 摸底、拆分任务、冻结材料、核对证据、处置发现、集成和交付 | 不把实现者自评当成独立复审 |
| 只读调查者 | 回答边界明确的事实问题，返回位置与原文 | 不裁决业务语义，不改文件 |
| 实现者 | 在授权和文件边界内完成单一意图的修改 | 共享工作区保持单一写入者，保护既有改动 |
| 独立审阅者 | 检查意图、实现责任、耦合前提及相关证据 | 不重新设计方案，不以风格偏好扩展范围，不重复运行构建和验证 |

角色不等于固定人数。主代理先查看目录、格式和少量原始样本，再决定是否拆分。只有相互独立且有并行收益的问题才分派；简单定位直接完成。模型和角色选择遵循项目配置，不在本页另设路由。

## 5. 一轮审阅的具体步骤

### 步骤一：明确范围和验收要求

查看 `git status --short`，识别用户和其他任务的既有改动。记录本次用户原话、已确认决策、可观察的完成条件、排除项和授权边界。

按风险列出需要证明的行为，尤其是输入如何进入或退出候选、状态变化的先后、失败或回退行为，以及输出被谁消费。局部修复可直接使用已确认的复现及其预期结果。语义有冲突时交回用户裁决，其他不依赖该裁决的工作继续。

### 步骤二：完成实现和相应验证，冻结审阅材料

对于已授权的修改，等整个功能完成后再发起最终独立复审。对于只读审查，直接冻结用户指定的版本和范围。

整理以下材料，低风险任务可直接在任务简报中列出，不强制新建一套文件：

| 材料 | 内容与检查点 |
|---|---|
| 用户要求 | 原文引用相关要求及裁决，保留来源，不用代理转述替换 |
| 审阅准绳 | 改动前的权威文档与已确认决策；标明版本 |
| 代码对象 | 起止 commit、改动文件清单和完整 diff，不能只给摘要 |
| 验证证据 | 已运行命令、输入、退出码、诊断和产物；明确未运行部分 |

已提交范围用 `git diff <base>..<head> --stat` 和完整 `git diff <base>..<head>` 定位，基线文档用 `git show <base>:<path>` 读取。这里的占位符需替换为实际值。

如果最终改动尚未提交，另保存 `git diff HEAD` 对应的跟踪文件变化，并用 `git ls-files --others --exclude-standard` 识别未跟踪文件，纳入本次相关文件的实际内容。明确材料对应哪个工作区状态；冻结后发生变化须更新材料，不能只写一个 HEAD 就声称覆盖了未提交改动，也不能混入其他任务的内容。

### 步骤三：按四个方向收集事实

| 方向 | 调查问题 |
|---|---|
| 调用方与下游 | 谁读取被改函数、结构和输出？改动前依赖什么顺序、非空条件、唯一写入或计算次数？ |
| 同类计算 | 哪些地方执行相同计算或判断，包括本次未改的文件？ |
| 旧路径残留 | 被替换逻辑是否仍有调用、分支、回退或兼容入口？ |
| 行为文档 | 哪些模块页、调用链页、接口页及其权威文档描述相关行为？本次是否同步修改？ |

每份调查交回 `路径:行号`、原文和查找范围。没有找到时说明查过哪里；来源有冲突时原样列出。调查结果不预先替审阅者宣布“实现正确”。主代理核对会改变判断的事实后，交给审阅者。

### 步骤四：在独立上下文中审阅

只传入用户原话、基线准绳、冻结 diff、事实清单和与证明要求有关的验证证据。审阅者先读要求，再检查实现和证据，围绕三个问题作判断：

- **符合用户意图吗？** 是否遗漏要求、多做功能、扩大范围或替换了用户裁决？
- **实现责任清楚吗？** 同一规则由谁保证，有无重复兜底、样例特判、冲突旧路径或无关改动？
- **耦合前提仍成立吗？** 调用方和下游依赖的顺序、状态、集合和输出语义是否保持，行为文档是否同步？

每条发现引用被违反的要求或下游前提，给出可核对的输入与后果；证据不足写“未查清”。涉及搜索、剪枝、缓存时检查保证等级；涉及排班和导出时检查最终状态及各输出层的一致性。具体输出格式服从所用复审角色。

### 步骤五：逐项处置并更新最终证据

主代理核对原始依据，将每条发现登记为：

| 结果 | 需要留下什么 |
|---|---|
| 已修复 | 改动说明、对应 diff 和修正后的验证证据 |
| 有证据驳回 | 能直接反驳发现的用户原话、规则、代码或运行证据 |
| 交给用户 | 需要裁决的具体问题、可选做法、后果和推荐 |

授权内的修复由单一写入者完成。修复后对最终集成状态运行相应验证，重新冻结 diff 和证据，再按风险补充独立复审。审阅者批准不能单独关闭任务，验证通过也不能掩盖未处置的意图偏离。

无人值守修复的轮数、暂停原因和交接字段直接遵循[质量总则的无人值守约定](QUALITY_AND_AUDIT.md#23-无人值守修复与用户裁决)，本页不另设循环机制。

### 步骤六：交付和关闭

报告先说明距离用户目标还有什么差距，再按三个审阅问题给出结论、例子和处理结果。列出实际验证的行为与规模、未运行或失败的检查、证明边界和延期项。没有发现的问题写“未发现”，不为凑数产生建议。

已授权修复按项目规则在验证完成后原子提交；只读审查交付报告即可。结束时再次查看 `git status --short`，说明剩余工作区状态。

## 6. 可直接使用的任务模板

以下是填写简报的辅助模板，不新增强制产物。占位内容按本次任务填写；审阅者应通过引用读取完整材料，不能只看模板中的摘要。

### 只读调查简报

```text
目标：只回答【一个可独立核对的事实问题】。
范围：允许读取【路径】，排除【无关领域】；不修改文件。
已知样本：【原始记录或代码位置】。
查找方法：【字段、符号、调用方或建议命令】。
交付：事实、路径:行号、原文或命令输出；不作业务裁决。
未知项：写清查过哪里；来源冲突原样返回，不自行调和。
停止条件：【哪些证据齐备后即可结束】。
```

### 独立审阅简报

```text
任务：独立审阅【冻结版本/工作区材料标识】中的完整变更。
先读用户原话和基线规则，列出应履行的要求，再读 diff。
材料：
- 用户要求与裁决原文：【引用位置】
- 改动前规则及版本：【引用位置】
- 完整 diff、改动范围和未提交文件内容：【引用位置】
- 调用方、同类计算、旧路径、行为文档的事实清单：【引用位置】
- 风险对应的运行证据和已知未覆盖项：【引用位置】
检查：符合用户意图、责任清楚、耦合前提仍成立。
发现须附要求或前提、具体触发输入、行为后果和原始证据。
检查相关断言能否区分合法与最小非法状态，说明保证边界。
不修改文件、不重跑构建和验证、不扩展架构或风格议题。
证据不足标“未查清”；按项目复审角色规定的格式返回。
```

### 发现与处置记录

| 编号 | 要求或下游前提 | 触发输入与行为后果 | 证据位置 | 处理结果 | 最终验证或待裁决项 |
|---|---|---|---|---|---|
| F1 | 填写原文依据 | 填写可核对的例子 | 填写路径与产物 | 已修复／有证据驳回／交给用户 | 填写本轮结果 |

## 7. v2 中的验证与工具入口

通用方法要求按风险选择验证；v2 的具体验收约束见[根规则](../../AGENTS.md)和[质量总则](QUALITY_AND_AUDIT.md)。本项目不新增、保留或运行源码单元／集成测试。

| 工作内容 | 当前入口 |
|---|---|
| 局部修复 | 最小反例、相邻反例和受影响的真实 CLI 入口；改候选时覆盖进入和被排除两侧 |
| 求解、编排、排班、导出等变更 | [终态不变量 skill](../../.agents/skills/arknights-invariant-gate/SKILL.md)：release CLI 的 `--assert-invariants`，以及代表性和 high-owned Box 批量运行 |
| 排班与导出一致性 | [体系一致性 skill](../../.agents/skills/arknights-system-audit/SKILL.md)：核对核心最终状态、profile／stdout 和 MAA 的对应事实 |
| 中高风险独立复审 | [意图复审 skill](../../.agents/skills/arknights-intent-review/SKILL.md)；Codex 使用 [sol-blind-reviewer](../../.codex/agents/sol-blind-reviewer.toml) |
| 需要留痕的证据工作流 | [证据工具说明](../../scripts/codex/README.md)：命令包装、产物登记、范围检查和报告渲染 |
| 文档与导航 | [文档生命周期](../文档生命周期.md)：更新行为 owner，生成索引并执行文档检查 |

批量通过只证明这些输入满足已注册的不变量，不证明全部机制、全部输入或全局最优。比较前后结果要保持输入和保证范围一致，并核对具体失败集合；失败数量相同不足以证明没有新增错误。

证据脚本可以核对命令状态、引用、文件和哈希等一致性，业务结论仍需按要求和行为判断。包装器的输入描述哈希也不能代替输入文件内容快照。实际参数和能力以[工具说明](../../scripts/codex/README.md)及脚本为准。

当前已具备协作规则、复审角色和证据辅助脚本；[质量总则](QUALITY_AND_AUDIT.md#23-无人值守修复与用户裁决)明确指出，持久写入锁、自动重试和通知运行时尚未实现。执行本指南时应记录实际完成的动作，不把流程约定写成已经自动执行的能力。
